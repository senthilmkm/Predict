🧹 Firestore purge jobs
Deletes old documents after each Cloud Scheduler /tick (same minute job as trading — no extra Cloud Run service). At most 400 deletes per minute. Off jobs are not queried.

These jobs permanently delete Firestore documents. That is not the same as hiding a row in the iOS app. Settings are stored in system/config next to the tick interval.

Never auto-deleted (no job for these):

  • User profiles users/{userId} — login, arm state, cushions, push tokens
  • Kalshi API keys in Secret Manager
  • system/config and system/catalog

Runs after trading sub-ticks in the same /tick request, so a fill just written cannot be deleted in that same pass. A second overlapping /tick skips purge (in-process lock). Firestore delete is idempotent.

Numbers in parentheses are current Firestore document counts across all users. They are not “how many will delete this minute.”

Audit logs (—)

Collection users/*/audit. Age field timestamp. DELETE the document. Default On, keep 30 days. This is the Audit & Errors tab, not the trade stream.

Dismissed alerts (—)

Collection users/*/alerts. Age field at. DELETE only if dismissedAt is set. Undismissed alerts are never deleted (same alertId would re-push). Phone “old alerts” only hides (sets dismissedAt). This job is the actual delete. Default Off, keep 90 days.

Closed trades (—)

Collection users/*/trades. Age field executedAt. DELETE — this is Live Trade Stream, History, and Cloud P&L for that fill. Open/pending fills are skipped (SUBMITTED, FILLED pending/exiting). Default Off, keep 365 days.

Last purge pass: Never

Ticking On does not start the job until you click Save purge settings. The page refreshes every 10s; unsaved ticks are kept until you Save or leave. Run once uses the Keep-for days saved on the server.

Unsaved changes — click Save purge settings or the On switch will not persist.

🔁 Kalshi retries

Platform-wide. Applies to the iPhone foreground poller and the GCP worker. On a matching error, Predict retries the same GET this many times, waiting the interval between tries. If it still fails, both sides pause all Kalshi calls for the pause seconds, then try again. Stored in system/config.kalshiRetry.

401 / 403 are never retried here (still a 5-minute auth block on the phone).

429 keeps the existing ~30s pause unless you add 429 to the HTTP list, then this policy wins.

POST / place-order is never immediately retried (could double-fill). A 5xx on place still starts the pause.

Unsaved changes — click Save retry settings.

3. Cloud Firestore Database Schema

  • • users/{userId}: User status doc (`cloudTradingEnabled`, `state: ARMED/DISARMED`, `config`, `pushTokens`).
  • • users/{userId}/trades/{tradeId}: Execution records (`status: FILLED/CANCELLED/SETTLED`, `notionalUsd`, `payPrice`, `fillCount`, `pnlUsd`).
  • • users/{userId}/audit/{logId}: Audit trail (`KEY_UPLOAD`, `KILL_SWITCH`, `TRADE_TRIGGERED`, `ERROR`).
  • • users/{userId}/alerts/{alertId}: Cloud alerts. Phone hide sets `dismissedAt`; Purge jobs can DELETE dismissed docs only.
  • • system/config: Tick interval + purge job On/Off and keep-for days. User profiles and secrets are never purged.

4. Race-Condition Protections

Each Cloud Scheduler /tick runs sub-ticks sequentially in that request. Same-contract buys are capped by max trades / asset / 15m window (in-tick claims + filled-buy count). Protect-sell uses a claim on the open fill. Two overlapping /tick requests are still possible if a request runs longer than the scheduler period.
